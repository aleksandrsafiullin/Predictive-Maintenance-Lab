## 3. Предлагаемый протокол разделения

### 3.1. Назначение групп

- **Train:** обучение весов, fitting scaler/imputer/encoder, настройка параметров baseline.
- **Validation:** архитектура, длина истории, лучший checkpoint, early stopping, правила алертов.
- **Test:** оценка уже выбранной и зафиксированной системы без последующего подбора на её результатах.
- **Demo:** режим показа, а не обязательная четвёртая выборка. Для разработки демонстрации использовать validation; для презентации зафиксированной модели можно последовательно воспроизводить test.

Не выдавать повторное воспроизведение test за независимый дополнительный эксперимент. Не подбирать модель или H/K по тому, на каком test-unit получается самый красивый алерт.

### 3.2. Подшипники

Сохранить существующий протокол:

| Группа | Экземпляры |
|---|---|
| Train | Bearing1_1–Bearing1_3; Bearing2_1–Bearing2_3; Bearing3_1–Bearing3_3 |
| Validation | Bearing1_4, Bearing2_4, Bearing3_4 |
| Test | Bearing1_5, Bearing2_5, Bearing3_5 |

Это проверка новых экземпляров при режимах, представленных в train. Она не доказывает перенос на неизвестный режим или промышленный фосфатный завод.

После исправления pipeline можно добавить 4-fold validation на 12 development-подшипниках: по очереди один из индексов 1–4 каждого режима становится validation. Три `*_5` не входят ни в один train/validation fold. Сравнивать модели по агрегированным validation-результатам, а не выбирать удачный fold. Для MVP это следующий уровень, не обязательный блокер первого полного прогона.

### 3.3. Фильтры

Сохранить авторский test. Текущий train/validation split со stratification по наличию события выглядит разумным первым протоколом.

Согласно implementation_report, в 50 авторских обучающих экспериментах только 5 наблюдавшихся пересечений порога 600 Pa: 4 в train и 1 в validation. Остальные 45 историй цензурированы: наблюдение закончилось без зарегистрированного пересечения порога. Они полезны для survival-модели, но не дают точного времени будущего события.

Не называть окончание такого эксперимента отказом. Не учить обычную RUL-регрессию на `observation_end - t` для цензурированных записей как на достоверном остаточном ресурсе. Не добавлять авторский test в train ради количества отказов.

Проверить происхождение и доступность `Train_Data_Uncensored.mat`. Если полные истории удастся экспортировать и верифицировать, создать отдельный протокол `filters_full_history`, не смешивая его результаты с censored-протоколом. Все версии одной физической истории должны иметь общий `origin_unit_id` и попадать только в одну группу. Публикация разных файлов не означает независимость экспериментов.

## 4. Исправления, необходимые до нового сравнения моделей

### P0-1. Единый preprocessing для train и inference

**Файлы:** `src/pdm/preprocessing.py`, `src/pdm/predict.py`.

При обучении `filters_feature_frame` создаёт `dust__...`. В replay `Predictor.predict_from_history` передаёт сырые строки напрямую в `Preprocessor.transform_frame`. Этот метод не создаёт one-hot из `dust`, а заполняет отсутствующие колонки сохранёнными fill values. Тип пыли в runtime-входе фактически заменяется константными значениями.

Изолированная проверка на двух категориях:

```text
Ожидаемые стандартизованные признаки: A -> [ 1, -1], B -> [-1, 1]
Текущий путь на сырых строках:        A -> [ 0,  0], B -> [ 0, 0]
```

Это синтетический пример, не значения реального scaler.

**Изменение:** один сериализуемый pipeline `raw features -> saved categorical encoding -> log transforms -> saved median imputation -> saved scaling` для обучения, validation, test и replay. Определить поведение неизвестной категории. Запретить повторное масштабирование уже преобразованного входа.

В том же методе существующие NaN/Inf заменяются нулём, хотя scaler при fitting использует медианные fill values. Воспроизведён пример: median=mean=2, scale=1; ожидаемый результат для пропуска 0, текущий -2. Использовать сохранённую train-медиану последовательно.

**Приёмка:** тензор одного и того же сырого окна в offline dataset и Predictor совпадает до допуска 1e-6; это проверяется для обеих dust-категорий, неизвестной категории и пропусков.

### P0-2. Правильная длительность для survival loss фильтров

**Файлы:** `src/pdm/windows.py`, `src/pdm/data/filters.py`, `src/pdm/train.py`.

Сейчас `build_windows` ставит `duration_s = observation_end_s - t` независимо от наличия события. При наблюдавшемся событии target RUL при этом рассчитывается от `event_time_s`. Weibull NLL использует именно duration, поэтому определения расходятся, когда порог достигнут до конца файла. После события также могут формироваться окна с `event=1`.

Воспроизведённый пример: событие t=20, конец наблюдения t=40, прогноз t=10. Правильная event-duration=10, текущая duration для loss=30. Дополнительно включаются два окна с t>=20. Влияние на конкретные пять событий исходного датасета не измерялось: проверить, совпадает ли у них первое пересечение порога с концом записи.

**Изменение:**

```python
if event_observed:
    if t >= event_time_s:
        continue
    duration_s = event_time_s - t
    event = 1
    target_rul_s = duration_s
else:
    if t >= observation_end_s:
        continue
    duration_s = observation_end_s - t
    event = 0
    target_rul_s = None
```

Сохранить отдельную возможность показывать датчик в момент события, но не оценивать её как заблаговременный RUL-прогноз. Для подшипников тоже согласовать train/test-маску: обучение исключает endpoint, а текущий replay его включает.

**Приёмка:** событие в середине записи, событие в последней строке, полностью цензурированная история и окно на границе события дают правильные метки; после события нет тренировочных risk-set окон.

### P0-3. Проверка совместимости данных и split при evaluation

**Файлы:** `src/pdm/evaluate.py`, `src/pdm/train.py`, `src/pdm/experiments.py`, `src/pdm/data/prepare.py`.

Run сохраняет свой `split.json`, но `evaluate_run` получает split из текущего `load_processed(dataset_id)`. После переподготовки данных можно оценить старую модель на новом test-наборе, который уже содержит её train/validation units. При неизменной конфигурации это не доказанная текущая утечка, а отсутствие необходимой защиты.

**Изменение:** evaluation/replay обязаны использовать snapshot разбиения и данных выбранного run либо прекращаться при несовпадении. Нужны проверяемые `dataset_version`, `raw/processed hashes`, `feature_pipeline_version`, `split_hash`, `checkpoint_hash`. Идентификаторы соответствуют физическим историям, не только именам файлов. `prepare` создаёт новую версию, а не незаметно меняет вход старых экспериментов.

**Приёмка:** изменение split, time scale, feature schema или processed data после обучения блокирует оценку старого checkpoint на новых данных. `train ∩ validation`, `train ∩ test`, `validation ∩ test` пусты; нет unassigned/duplicate units; проверяется и пересечение исходных origin IDs.

### P0-4. Единые правила разрывов и качества входа

**Файлы:** `src/pdm/windows.py`, `src/pdm/predict.py`, `src/pdm/replay.py`.

`build_windows` исключает окна через `gap_before`, а Predictor берёт последние H строк без такой проверки. Перенести проверку и в inference. После разрыва возвращать `Collecting history` до накопления H последовательных допустимых точек. Сбрасывать подтверждение алерта. Проверить уникальность и монотонность timestamp, достаточную длину и конечность значений.

Дополнительная причинная проверка: в адаптере фильтров threshold для gap определяется через median dt всей траектории. Для строгого streaming использовать документированный sampling interval или правило, которое оценивается только по доступному префиксу. Проверять причинность начиная с raw adapter, а не только с уже подготовленного массива.

### P0-5. Время фильтров и разрешённая интерпретация

**Файлы:** `configs/filters.yaml`, `src/pdm/data/filters.py`, `src/pdm/data/prepare.py`, UI.

`time_to_seconds=60` — зафиксированное допущение, не подтверждённая в текущем отчёте единица исходных Time/RUL. Не менять его на другое произвольное число. Проверить первичный источник/экспорт и что Time и RUL имеют совместимые единицы.

До подтверждения выводить заметное предупреждение и сохранять оригинальные единицы в метриках/экспортах. Не обещать предупреждение за конкретные реальные минуты. Если коэффициент меняется, создать новую версию данных, пересобрать окна, переобучить модель и пересчитать метрики.

## 5. Разделение evaluation и replay

### P1-1. Immutable evaluation

Разделить prediction и alert evaluation. Прогноз RUL не зависит от H/K. Он сохраняется с identity checkpoint/data/split. Пересчёт H/K повторно запускает только alert engine.

Вместо перезаписи `predictions.csv`, `alerts.csv`, `test_metrics.json` единственным набором файлов создать:

```text
runs/<run_id>/
  config.yaml
  split.json
  dataset_fingerprint.json
  preprocessing.json
  best.pt
  training_history.csv
  evaluations/<eval_id>/
    evaluation_config.json
    predictions.csv
    alerts.csv
    metrics.json
    metrics_by_unit.csv
```

Evaluation identity включает checkpoint, data version, split, evaluate mask, H, K, reset policy и версию метрик. Финальный report нельзя заменить экспериментальной настройкой без создания нового eval_id.

### P1-2. Исправить replay UI

**Файл:** `src/pdm/app.py`.

1. Изменение H/K сейчас меняет элементы интерфейса, но сохранённые `alert_status` и `alerts.csv` остаются от предыдущего Evaluate. Обновлять alert engine автоматически или явно показывать stale state и блокировать несогласованный статус.
2. Alert log сейчас отображает весь CSV без фильтра по unit и текущему времени. В демонстрации показывать только выбранный unit и `timestamp_s <= replay_time`. Полный лог доступен в ретроспективном evaluation, отдельно.
3. `_auto_refresh` вызывает fragment, обновляющий только подпись worker. Увеличение replay_step и графики расположены снаружи fragment. Перенести replay-state и нужные графики в обновляемый fragment либо правильно организовать rerun. Дефект подтверждён чтением кода и документации, но не браузерным запуском.
4. `_live_prefix_charts` без predictions.csv рисует только датчик и не вызывает Predictor. Реализовать настоящий on-demand prefix inference или честно заблокировать Play до подготовки прогнозов.
5. Ключ состояния replay должен учитывать dataset, run_id, unit_id и eval/policy identity. Смена модели или политики не должна оставлять состояние предыдущей демонстрации.

Воспроизведение заранее причинно рассчитанных prediction-ов допустимо. Главное — корректно подписать historical replay, не подавать будущие строки модели и не показывать зрителю будущие алерты.

Вместо JSON как основного представления — summary и таблица по unit.

**Подшипники:** главный агрегат equal-weight unit MAE; дополнительно pooled MAE/RMSE, переоценка остаточного ресурса, одинаковое сравнение с baseline, результат каждого из трёх test units. Добавить качество ближе к событию по заранее определённым временным зонам, не подбирать зоны по test-результату.

**Фильтры:** главная RUL-метрика — одна последняя доступная точка на каждый авторский test-префикс. Все prefix points — дополнительный backtest, не тысячи независимых тестов. Для censored validation сохранять NLL по всем units и отдельно MAE по наблюдавшимся событиям с их числом.

**Алерты:** lead time до события, число своевременных/поздних/слишком ранних предупреждений, пропуски при достаточном наблюдении, недостаточное покрытие, число эпизодов и длительность warning. Доля времени должна считаться через реальные Δt, а не только число строк при неоднородном sampling. Проверять все эпизоды по зафиксированному правилу: текущая сводка рассматривает только первый.

### Demo / Historical Replay

Выбор сохранённой модели и eligible unit; метка split; сенсор; прогноз RUL и baseline; H; текущая позиция; время предупреждения; лог только до текущего времени. Ground truth — отдельный evaluator-overlay без влияния на predictor. В конце — итог по этому unit и сравнение с общей test-таблицей.

Для фильтра, чей файл заканчивается до события, писать `End of observed data`, а не показывать выдуманное достижение 600 Pa. Дополнительное известное по метке время события не является наличием будущих сенсорных измерений.

## 7. Горизонт предупреждения

Текущая логика RUL <= H с K подтверждениями корректно обозначена в UI как порог, а не гарантия. Но `timely` сейчас означает любое предупреждение между event-H и event: даже предупреждение за секунду может попасть в timely.

Разделить:

- `H_trigger`: при каком прогнозе активировать предупреждение.
- `minimum_action_lead_time`: сколько времени нужно пользователю на действие.
- Допустимые ранние предупреждения/максимальный полезный горизонт, если это требуется сценарием.

Оценивать реальный `lead_time = event_time - confirmed_alert_time`. Учитывать задержку K-1 валидных шагов. Подбирать policy на validation; final test использует замороженную policy. Интерактивное изменение policy на test допустимо как исследовательский сценарий, но не как новый независимый final score.

| `test_labels_do_not_affect_predictor` | Изменение ground truth через реальный pipeline не меняет prediction |
| `test_evaluate_rejects_changed_dataset_or_split` | Старый checkpoint не оценивается на незаметно изменённом датасете |
| `test_alert_policy_cache_invalidation` | H/K меняют алерты, не прогноз RUL; устаревший cache не показывается |
| `test_replay_log_has_no_future_rows` | Вывод ограничен выбранным unit и текущим t |
| `test_replay_play_advances_without_clicks` | Браузер: время и графики меняются автоматически, Pause останавливает |
| `test_filter_endpoint_baseline_comparison` | Обе модели сравниваются на одинаковых endpoint-точках с coverage |
| `test_insufficient_coverage_not_false_miss` | Обрезанный префикс без достаточного интервала не объявляется пропуском |
| `test_alert_multiple_episodes_and_time_weighting` | Метрика корректна при нескольких эпизодах и неодинаковых Δt |

Существующие тесты на leakage полезны, но некоторые проверяют уже подготовленные массивы или изолированную модель вместо полной цепочки, поэтому пропуск one-hot в Predictor они не ловят.
