# Create ML workflow: implementation master plan

## Outcome and scope

Build a local, persistent Streamlit workflow: **Projects → Create project → Import data → Data Quality → Training → Results**. A user can create and delete independently named projects; import a source folder with automatic unit-level holdouts or separately supplied Validation and/or Testing folders; inspect those three sets; choose one eligible model engine and its parameters; train; then play a single sensor chart. The chart shows observed signal in gray, yellow/red limits, and a saved model's future signal forecast from the observation prefix at the current play position. It reports a red crossing only when the saved forecast and a compatible threshold rule support one. Deletion moves owned files to recoverable archive. Keep the existing Python/Streamlit/PyTorch stack and established research capabilities without exposing an old report chooser in this product flow.

## Current architecture and boundaries

- `src/pdm/app.py` discovers only `bearings` and `filters` via `LABELS`, stores `workflow_dataset` in session state, and renders the old Data Quality dump. `future_red_ui.py` trains binary classifiers for weak future-red labels. Those probabilities cannot be drawn as a future signal trajectory.
- `data/prepare.py`, `splits.py`, `preprocessing.py`, `worker.py`, `monitoring/signal_forecast.py`, and `monitoring/runtime.py` provide useful versioning, physical-unit split checks, worker execution, and actual multi-horizon signal forecasting, but many paths and profiles key on the two dataset IDs. The saved sensor models currently use persistence, causal trend, or quantile boosting, separate from the GRU/LSTM/Fly/Random/Full CNS future-red model matrix.
- `runs/_worker` is global and admits one heavy job. New jobs must include project ID, job ID, source/snapshot ID, and run ID to avoid displaying another project's status.
- `data/raw/bearings` is several GB. Register existing Bearings/Filters datasets as **linked legacy projects** that point to their current raw/processed/research locations. Do not duplicate raw files. Deletion archives the link's owned metadata/signal-run root and records a tombstone for the external binding; never deletes legacy raw/processed/research paths. New projects use scoped paths and own their files.
- Preserve existing GRU/LSTM/Fly/Random and bearing Full MaleCNS capabilities. Stale `.cursor/commands/orchestration.md` and skill/agent defaults refer to GRU/LSTM-only and older filter time wording; follow current code and `docs/data_units_and_endpoints.md` for the established capabilities and seconds contract. Full MaleCNS remains bearing-only and unavailable for this new signal task until an actual signal readout/inference implementation and prerequisites are verified. Do not pass a binary classifier as a signal engine.

## Frozen interfaces for parallel development

- **Serializable DTOs:** interfaces return plain mapping/list/scalar values (implementation may use `TypedDict`), never opaque custom objects across A/B/C. Persist JSON manifests and Parquet tables. `ProjectStore(root: Path | None = None)` defaults to `data/projects`; `project_store()` uses `PDM_PROJECTS_ROOT` for test isolation. Methods: `create(name, source_kind)`, `list()`, `get(project_id)`, `update(project_id, **allowed_fields)`, `archive(project_id)`, `register_legacy()`. A project mapping has `project_id`, `name`, `source_kind`, `storage_mode`, `state`, `source_manifest`, `active_snapshot_id`, `selected_run_id`, `schema_version`, `created_at`. All owned metadata lives under `root/{project_id}`; the helpers `project_path(pid)`, `snapshot_path(pid, sid)`, `run_path(pid, rid)` safely resolve owned paths. Linked legacy records also get a tiny owned metadata root, without copying raw data. `update` is the run-selection operation; it validates a run bound to that project/snapshot before setting `selected_run_id`.
- **Import/snapshot:** `import_project(project_id, source: ImportSpec) -> dict` and `prepare_project(project_id, source_manifest_id) -> dict`. `ImportSpec` is JSON serializable and names staged primary/validation/test sources, independent `auto`/`folder` modes, seed, desired weights, signal schema and threshold rule. `load_snapshot(project_id, snapshot_id=None) -> dict` returns `features` DataFrame with canonical `unit_id,timestamp_s,signal,gap_before` plus only declared optional input columns; `units` DataFrame; `split` mapping with train/validation/test unit lists; `report`, `schema`, `fingerprint` mappings; and `snapshot_id`, `project_id`, `dir: Path`. `schema` has `source_kind`, original `signal_column`, `signal_label`, `signal_unit`, `time_unit='s'`, `input_columns=['signal']` for generic v1, `output_domain='real'` for generic signed signals, and `thresholds={direction,yellow,red,mode}`. Mode is `absolute` or, for bearing linked snapshots only, `initial_baseline_multiple` computed from causal initial history. Snapshot root contains `features.parquet`, `units.parquet`, `split.json`, `data_report.json`, `feature_schema.json`, `processed_fingerprint.json`; activation follows full hash validation. A's tests provide a tiny contract fixture imported by B/C tests.
- **Signal/run:** `available_signal_engines(pid, sid) -> list[dict]` with `engine_id,label,available,reason,params`; `train_signal_run(pid, sid, engine_id, params, *, should_stop, status_cb) -> dict`; `list_project_runs(pid) -> list[dict]`; `load_signal_run(pid, rid) -> dict` with manifest and verified artifact paths. `forecast_prefix(pid, rid, unit_id, as_of_s) -> dict` uses exact keys `as_of_s`, `observed_prefix`, `points` (each `target_time_s,value,lower,upper`), `thresholds`, `crossing` (`status,time_s`), `project_id`, `run_id`, `snapshot_id`, `status`, `reason`. Points use positive supported horizons; `None` means an unavailable interval, not an invented bound. Future rows are absent from inference input. Run records are project/snapshot bound; UI unlocks Results only for a verified signal run, not an old classifier/RUL run.
- **Worker:** new jobs are `project_import` and `project_train` with `job_id,project_id` plus source/snapshot references. `spawn_worker(job)` acquires an atomic launch lock before writing the queued job and starting a process. Every queued, running and terminal status, including exceptions, has `job_id,project_id,kind,status,stage,progress,message,error`; `status_for_project(pid)` filters. `request_stop(expected_job_id=None)` preserves old callers, but with an expected ID rejects a mismatch; stop acknowledgment and terminal status are tied to that job. `archive()` refuses while matching queued/running work exists or its process still lives; a completed status alone is insufficient. Existing worker APIs remain backward compatible.

## Product and scientific contracts

1. **Project record** (`src/pdm/projects.py`): immutable safe `project_id` (UUID/slug), mutable unique display name, `source_kind` (`xjtu_bearings`, `hse_filters`, `generic_sensor_csv`), `storage_mode` (`owned`, `linked_legacy`), creation time, source manifest, active processed snapshot, selected run, and schema version. Registry JSON updates are atomic and lock protected. Every project route resolves a project record before deriving a filesystem path; reject traversal/symlink escapes for owned paths. Never infer projects from two hardcoded labels. Legacy registration is idempotent and conditional on actual artifacts. On demand, wrap a legacy prepared table/split as a small immutable project snapshot (normalizing canonical fields); do not copy raw multi-GB data or treat old model artifacts as signal-ready. New project can have the same source kind as another and its own artifacts.
2. **Import**: Create project persists an empty record before import. The primary input is **Choose folder** via Streamlit 1.63 `st.file_uploader(..., accept_multiple_files="directory")`; a server-visible folder path is the secondary option for large sources, with ZIP/files retained where appropriate. Browser directory entries preserve relative paths after sanitization, with upload-size/resource guidance; never trust `UploadedFile.name`. Start with one Training pool. Validation and Testing each independently choose **automatic holdout** or **separate folder**. The default desired weights are 70/15/15. When one manual folder is supplied, renormalize the weights of the remaining automatic groups over the primary pool (for example Train:Test = 70:15); manually supplied units lie outside this ratio. Show actual whole-unit counts, refuse infeasible allocations, and never mix supplied holdouts into training. Explicit folders must not overlap in physical history or content fingerprint. For generic CSV, require `unit_id`, `timestamp_s`, selected finite numeric signal and declared signal unit; one or more CSV per physical unit are accepted, no RUL/failure labels required. Ask for instantaneous yellow/red limits and direction; do not infer industrial fault limits. New XJTU/HSE projects pass their owned raw directory to `extract_bearings_features`/`extract_filters_tables` and write scoped snapshots; do not call the global `prepare_dataset(dataset_id)` default. HSE official author-test histories remain Test only regardless of custom/manual settings, and official RUL stays evaluation-only; custom ratios partition author-train units. Validate all before committing a source manifest.
3. **Prepared snapshot**: include `project_id`, source content digest, source adapter and schema, split protocol/seed/desired weights/realized counts, disjoint physical-unit assignments, feature schema, quality admission decisions, observed/censored outcome semantics where applicable, and a version. Reuse immutable snapshot/fingerprint patterns. A rejected/missing signal row creates an explicit gap; no training or replay window crosses it. Split and preprocessing are fit/derived on training units only; validation chooses model/parameters; test is read once after freeze. Unknown future targets at censoring, gaps, and ends remain masked. Never randomly split rows/windows from one unit.
4. **Model/run**: a run is bound to one project and one snapshot, one selected engine, exact parameter schema, target signal, horizon grid and time units, threshold-rule version, preprocessing artifact, validation selection, and hashes of model/prediction artifacts. The signal-task capability registry initially launches **GRU**, **LSTM**, and a generic-adapted **multi-horizon quantile boosting** sensor method. Its snapshot-derived profile must not call `monitoring/contracts.dataset_profile()` for generic IDs or assume HSE `flow_rate`/`dust_feed`. Generic v1 inputs are allowlisted to causal `signal` history; signed generic output has real domain and is never nonnegative-clipped. Reuse causal sequence/model kernels for GRU/LSTM but fit new numeric signal heads; train-only fit and validation selection remain required. Persistence/local trend remain honest comparison baselines. Existing Fly, Random, and bearing Full CNS classifier/RUL research paths remain in code/CLI with tests, but are listed as unavailable for the new signal target with a precise reason. Do not offer them in the launch control until a validated signal readout exists. Engine eligibility is explicit per project. The old future-red classifier is preserved as an API/CLI artifact, not a result curve or advanced branch in the new project UI.
5. **Replay contract**: worker computes/caches forecasts for test units at eligible observation prefixes from only `timestamp_s <= as_of`, using the saved model and train-fitted preprocessor. UI receives observed prefix, forecast points for positive future horizons, threshold trace/rule, and saved run binding; hidden later observations may be revealed only as playback advances and never as inputs to earlier forecasts. Gray observed signal stops at the play cursor. Yellow/red limits use native signal units; if context makes a limit dynamic, draw its actual stepped rule or explain why a horizontal line is unavailable. A red crossing is the first supported forecast point crossing an instantaneous red rule; for sustained rules, report no crossing time unless duration is established. Show forecast horizon and uncertainty calibration status; do not splice forecasts to hidden truth, interpolate unsupported horizons, manufacture uncertainty, or convert future-red risk into a curve. State 'no crossing predicted within shown horizon' or 'unavailable' as appropriate, never infinite life.

## Execution and review discipline

Use the repo's planner → plan reviewer → developer → code reviewer loop. Review this scoped plan before implementation, then implement in dependency order with review/fix for each subtask. Reviewers must check user-visible behavior, project isolation, unit/snapshot leakage, causal replay and scientific wording. Existing dirty files are preexisting user work; do not revert or overwrite unrelated edits, and inspect current diff before touching each owner file. Preserve historic `.cursor/tasks/master-plan.md` and tasks. New planning files live only in this directory.

## Verification and end-to-end acceptance

- Focused invariant, registry/import/split, model numeric/finite-gradient, worker AppTest, and replay tests are listed in task files. Final: `.venv/bin/python -m pytest tests -q` and `.venv/bin/python -m ruff check src tests`; include scripts when changed. Do not equate a smoke run with model quality.
- Fresh workspace: create A and B, import separate generic CSV folders, restart Streamlit, see both persistent projects; delete A and verify A's owned files moved to recoverable archive with receipt while B and linked legacy files/runs remain. During an A job, deletion must first stop/wait or refuse; B must never display A status.
- Import a folder through browser and a large folder through server path. Exercise automatic split, only Validation manual, only Testing manual, and both manual; verify disjoint physical-unit membership, minimum-unit errors, snapshot binding, duplicate/content collision rejection, failed import rollback, right-censored/missing future targets masked, and train-only preprocessing. Data Quality must show comprehensible Train/Validation/Test summaries and a selected unit plot, without `dataset_version` debug content in the primary view.
- Train one selected eligible engine on a small real fixture with user-set parameters, validate, freeze, evaluate test once, restart app, reopen exact saved project/run. Full CNS availability is honest and does not block standard engines. Existing legacy research APIs, CLI and artifacts remain readable; the new product has one Results view, with no old report chooser.
- Play on held-out unit: at each cursor, observed gray ends at cursor; recompute/check saved forecast from the same prefix in an isolated process, then perturb/delete all future rows and assert identical forecast and crossing. Compare against a deliberately leaking model to make test meaningful. Check yellow/red traces, units, horizon and no-crossing/unavailable text. Browser QA at desktop/mobile widths and console clean. Document actual model metrics and any uncalibrated limits; never claim predictive quality from smoke.

## Decisions for plan review

- Generic sensor CSV is **required** for arbitrary new projects. Without it, Create project would only rename the two datasets. Limit generic v1 to one selected numeric signal and unit/time columns; other source formats stay adapter-specific.
- Streamlit 1.63 supports browser directory upload; use it for manageable folders and a server-visible path for multi-GB inputs. It uploads browser file contents through memory, so folder selection is not a direct server filesystem picker. [Streamlit file uploader](https://docs.streamlit.io/develop/api-reference/widgets/st.file_uploader).
- Existing linked datasets register without copying raw files; deletion archives their owned metadata/signal-run root and tombstones the external binding while preserving legacy raw/processed/research paths. New owned projects use isolated directories. Deletion is explicit, project scoped, checks active jobs and symlink boundaries, and uses a recoverable trash move before later purge.
- User-selected engine means one model family per run. The first launchable signal engines are GRU, LSTM, and multi-horizon quantile boosting. Fly, Random and Full CNS existing research paths remain intact but are not eligible for this signal task until a genuine signal head and causal runtime are implemented and verified. Existing future-red classifiers remain preserved and separate from the new signal report.
